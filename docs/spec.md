# Portfolio Performance CLI: holdings, transaction history, and safe transaction recording

## Problem Statement

The portfolio owner currently relies on the Portfolio Performance application to inspect holdings and transaction history, record purchases, sales, and dividends, and import Smartbroker statements. They want to perform these tasks from a Python CLI that directly reads and updates their existing portfolio XML, while continuing to use Portfolio Performance for FIFO matching and profit calculations.

An XML document that merely parses is insufficient. Incorrect cash/securities links, reference IDs, monetary values, or quantity history could silently corrupt the portfolio. Repeated imports, incomplete statements, external edits, and failed writes must not introduce duplicate transactions or lose existing data.

## Solution

Provide a Python application managed with Astral uv and a pyproject-based project definition. It offers simple text queries for current holdings and transaction history, manual recording of purchases, sales, and dividends, and import of one supported Smartbroker PDF at a time.

Every mutation previews its proposed changes by default. An explicit `--apply` writes after validation without another interactive prompt. Supported ID-reference XML is updated in place through atomic replacement, with a preserved daily backup. Unsupported formats, untested versions, missing information, contradictory amounts, uncertain duplicates, invalid historical quantities, and stale previews prevent application.

The CLI runs independently of Portfolio Performance during normal use. Compatibility tests use a pinned upstream Java reader to establish that generated XML loads into the expected financial model. Import bookkeeping lives in an adjacent metadata file rather than custom XML fields or transaction notes, as required by the existing ADR.

## Implementation Decisions

- **Runtime and scope.** Build a Python CLI managed with uv and a pyproject-based package definition. Normal commands must not launch or depend on the Portfolio Performance application or its Java runtime. The initial audience is the portfolio owner.
- **Domain vocabulary.** Use security, holding, securities account, cash account, purchase, sale, dividend, transaction history, and holding last updated with their existing glossary meanings. A sale reduces held quantity; it does not delete a security or historical purchase.
- **Module responsibilities.** Provide command/configuration handling, portfolio persistence and compatibility validation, holdings/history queries, transaction planning and validation, broker PDF extraction, import bookkeeping, and safe application/backup management. These are responsibilities rather than a mandated one-module-per-responsibility structure. Keep the public command boundary small; do not expose XML internals through it.
- **Supported representations.** Initially read and write tested Portfolio Performance ID-reference XML. Reject untested model versions and unsupported representations before mutation. A successful XML parse does not establish support. Declare tested application release, exact upstream source revision, and XML model version separately in a support matrix.
- **Preservation.** Preserve unrelated data in supported portfolios, including existing security definitions, transaction history, settings, classifications, and reference relationships. Purchases and sales must create consistent linked securities-account and cash-account entries. Dividends create security-associated cash credits with applicable fees and taxes without changing held quantity.
- **Portfolio Performance remains the calculation authority.** Derive held quantities from quantity-changing transactions for queries and historical validation. Do not calculate or persist FIFO allocations, realized gains, or current market valuations. The upstream application continues to derive its own FIFO and profit results.
- **Security and account resolution.** Reuse an existing security when identified unambiguously; create a security definition when needed for a purchase. Resolve the selected securities-account/cash-account pair before planning a purchase or sale. Dividends use the selected cash account. Missing or ambiguous required account references are errors, rather than reasons to select an arbitrary account.
- **Configuration precedence.** Discover configuration in the current working directory unless `--config` is supplied. Configuration stores the portfolio path and default account pair. `--file` overrides that path; command-line account parameters override account defaults. With no selected portfolio path, use `portfolio_performance.xml`. Resolve configured relative paths from the configuration directory and an explicit relative `--file` from the current working directory. The configuration filename is an implementation detail not settled by the interview; document the chosen name without interpreting the XML filename as a configuration filename.
- **Monetary input.** Accept the available quantity, price, gross value, booked total, fees, and taxes as appropriate to the transaction type. Derive missing values only when the supplied values determine them. Use decimal arithmetic and the tested upstream representation's scaling and supported rounding. Reject supplied values inconsistent beyond supported rounding, and reject unrepresentable precision rather than silently losing information. For PDFs, retain the statement's booked amount as authoritative.
- **Currencies.** Support foreign-currency transactions with explicitly supplied or extracted exchange rates. Preserve relevant currency amounts, fees, taxes, and rate semantics according to the supported model. Required missing exchange information prevents application; do not fetch rates automatically.
- **Dates and quantity history.** Accept backdated transactions and date-only input. Use `11:00:00` for missing times, show it in preview, and retain supplied times. Validate a sale against the complete affected security/securities-account quantity history: quantity must remain nonnegative at its date and thereafter. Use a deterministic ordering where timestamps tie and do not introduce FIFO calculations.
- **Queries.** Holdings support security identifier/name and securities-account filters; sorting by name, quantity, or holding last updated; and zero-holding omission by default. Holding last updated is the latest quantity-changing transaction for that security in that securities account. Default to latest updates first. History supports those filters plus transaction type and date range, and chronological sorting with newest first by default. Both commands use stable ordering and `--limit` defaulting to 15, with zero meaning unlimited. Output is simple text presenting held quantities and recorded transaction amounts, without profit or current market valuation.
- **Preview/application contract.** All mutation commands preview by default, reporting affected security/accounts, transaction type, quantity where applicable, date/time, monetary values, currencies, and supplied or derived information. Preview changes neither XML nor bookkeeping and does not create or prune backups. `--apply` performs full validation and writes without another interactive prompt. A prior preview does not authorize applying to a different input state; revalidate the input before replacement.
- **PDF import contract.** Accept one PDF per invocation. Support the owner's current representative purchase, sale, and dividend layouts; select an upstream extraction reference from actual document bank identifiers and layout rather than the Smartbroker name alone. Pin the reference revision. Command-line parameters may supply missing information and must be visible in preview. Contradictory extracted financial values are errors, not override candidates. A PDF containing multiple recognized transactions is one atomic import: unsupported, ambiguous, missing-required, or invalid transaction content prevents all financial changes from that import.
- **Duplicate decisions.** Use document identity and broker references to detect confirmed re-imports, with evidence tied to the associated portfolio transaction IDs. Skip confirmed duplicates. Similar dates, amounts, prices, and transaction details without sufficient identity evidence are suspected duplicates and require an explicit override. `--apply` alone is not that override; unattended application stops on unresolved uncertainty. Do not assume a document is new merely because bookkeeping is unavailable.
- **Import bookkeeping ADR.** Store document hashes, broker references, and associated transaction IDs in an adjacent metadata file. Do not add custom XML fields or put bookkeeping in user-visible transaction notes. Missing or inconsistent metadata, including after external edits or backup restoration, falls back to suspected-duplicate checks. Coordinate metadata and financial changes so failed application cannot leave trustworthy-looking evidence for an import that was not applied; inconsistent evidence must never authorize an unsafe repeat import.
- **Daily backup.** Before the first successful portfolio change of a Europe/Berlin calendar day, create an adjacent backup named `<filename>.YYYY-MM-DD.bak` from the original input if that backup does not already exist. Never overwrite an existing daily backup. Failure to create a required backup prevents writing.
- **Backup retention.** After a successful write, prune only backups belonging to this tool. For the current Europe/Berlin calendar month and preceding 23 months, retain the three most recent daily backup dates in each month, or all available dates when fewer exist. Remove older tool-owned dates outside that window. Preview, failed operations, and skipped re-imports do not trigger pruning.
- **Safe replacement.** Validate the complete proposed transaction set before writing. Replace the portfolio atomically and reject application if the input changed since the validated preview/input snapshot. Require Portfolio Performance to be closed during application. A validation or pre-replacement write failure leaves the original portfolio intact; a failure of bookkeeping or backup pruning after a successful portfolio replacement must be reported accurately and must not encourage repeating the financial import.
- **Maintenance documentation.** Complete the existing manual extractor and version-support guides with the chosen pinned revisions, supported layouts, compatibility matrix, actual test commands, and known limitations when implementation establishes them. Extractor updates and XML support updates are separate contracts. Respect upstream licensing and attribution when adapting code or fixtures.

## Testing Decisions

- **Primary seam: the public CLI against a temporary portfolio.** The repository has requirements and domain documents but no implementation or existing test suite. Introduce one primary acceptance seam by invoking the real CLI with temporary anonymized portfolio/configuration/metadata files and asserting exit status, text output, resulting financial records, and filesystem effects. Exercise the actual configuration, parsing, planning, validation, and persistence paths together. The owner confirmed these testing seams before publication.
- **Test externally visible behavior.** Assert the financial model, preserved history and unrelated content, output semantics, duplicate decisions, and changes or lack of changes to files. Avoid private helpers, serializer call counts, mocked XML construction, and formatting snapshots that fail on harmless text changes. Byte comparisons are appropriate for a failed operation that must leave the original file unchanged; successful mutations require semantic comparisons rather than a mandated XML whitespace layout.
- **Query coverage.** Cover holdings across accounts, partial and full sales, zero-holding omission, holding last updated unaffected by dividends/metadata edits, historical records for closed holdings, every promised filter and sort, stable ties, default limits, unlimited output, and exclusion of current market/profit calculations.
- **Manual transaction coverage.** Cover existing and newly created securities, purchase cash/securities links, partial and full sales, dividends with fees/taxes, decimal derivation and inconsistent input, precision boundaries, foreign-currency rates, date-only fallback, explicit times, and account ambiguity. Inspect the resulting records and preservation of existing data.
- **Historical validation coverage.** Include a backdated sale valid on its own date but making a later holding negative, a valid backdated transaction, account-isolated histories, and timestamp ties. Rejected changes leave the portfolio unchanged.
- **PDF coverage through the same CLI seam.** Use anonymized representative PDFs for each supported current layout, with purchase, sale, dividend, foreign-currency, and multi-transaction cases. Assert extracted and supplemented values in preview and written records on application. Any invalid, unsupported, ambiguous, contradictory, or incomplete transaction in a document prevents the entire import.
- **Supporting extraction contract.** Retain representative PDFs and extracted-text fixtures preserving whitespace and line structure. Test PDF-to-text behavior and expected extracted transaction values separately where needed to diagnose layout regressions. Upstream text fixtures alone cannot prove the local PDF conversion works. Keep previous supported layouts as regression cases and record the reference revision.
- **Duplicate and bookkeeping coverage.** Cover repeat imports by document identity and broker reference, suspected monetary/date matches, explicit overrides, unattended refusal on uncertainty, missing metadata, stale transaction IDs, external portfolio edits, and restoring a backup. Check that confirmed skips add no transactions and that failed application cannot create misleading import evidence.
- **Preview and filesystem coverage.** Verify preview does not modify XML/metadata or manage backups. Cover `--apply` without another prompt, configuration discovery and override precedence, path-resolution rules, atomic application of a document's transaction set, stale input rejection, backup creation failure, existing daily backup preservation, Europe/Berlin day/month boundaries, retention across 24 calendar months, and preservation of files not owned by the tool. Failure injection may be used at filesystem boundaries; assertions remain about file preservation and reported outcomes.
- **Compatibility oracle: pinned upstream Java reader.** Load successful outputs with the reader for each declared supported release/revision/model-format combination, then inspect quantities, transaction types, dates/times, amounts, fees, taxes, currencies, security references, and linked account entries. Loading without model inspection is insufficient. Cover purchase, partial sale, full sale, dividend, foreign currencies, multiple accounts, and unrelated settings/classifications. Verify unsupported representations/model versions fail before writing.
- **Prior art and fixture discipline.** There are no local tests to extend. The recorded maintenance guides point to upstream broker extraction tests and core persistence/model loading as prior art. Establish anonymized versioned fixtures and reproducible commands during implementation; do not treat the owner's real portfolio as a committed test fixture or claim that an upstream compatibility check has already run.

## Out of Scope

- Binary, compressed, encrypted, protobuf, and XPath-reference portfolio editing; these require a later representation-specific specification.
- Reimplementing FIFO matching, realized gains, profit reporting, current market valuation, or persisted trade results.
- Automatic exchange-rate lookup, market-price retrieval, or other live financial-data services.
- Security/transaction deletion, removal of historical purchases after a sale, and a general-purpose portfolio repair or migration tool.
- Brokers and historical statement layouts not represented by the initial supported Smartbroker fixtures.
- Batch import of multiple PDFs in one invocation. Multiple recognized transactions within one PDF remain in scope.
- JSON output, a separately formatted table output mode, a GUI, and multi-user service operation.
- Automatic synchronization with upstream importers or automatically allowing new Portfolio Performance versions.
- Concurrent writing while Portfolio Performance is open.
